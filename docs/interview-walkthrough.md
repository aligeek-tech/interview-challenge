# Technical review walkthrough

Use the repository and executable tests to explain each guarantee. Start with the narrow business capability: a customer reserves finite voyage capacity temporarily, then either consumes that reservation to confirm or releases it through cancellation/expiry. The central invariant is reserved plus confirmed units never exceeding voyage capacity.

1. Show the Event Storming model and its seven resolved hotspots. Explain why Booking Capacity is one bounded context, why `VoyageCapacity` owns holds, and why `Booking` separately owns logical request identity. A table, aggregate and deployable service are different boundaries.
2. Open `BookingPersistenceSession.LockCapacityAsync` and the migrations. Explain READ COMMITTED, voyage row locking, the universal lock order, database checks and the partial active-hold unique index. Show that all competing writes retain the voyage lock until commit.
3. Run the twenty-session test. Describe how it observes actual PostgreSQL lock waiters before releasing them. Show the one successful hold, nineteen business rejections, and persisted counter/record reconciliation. A safe retry does not imply that a sold-out request should be retried automatically.
4. Explain the deadline decision before showing code. After all business locks, sample database time; strict less-than can confirm, equality/later expires. A request that arrived early may still lose after waiting. A successful pre-deadline decision can commit later. Show why transaction-start `now()` would be wrong for this rule.
5. Run the confirm/expire tests. Identify the exact blocking point, when each transaction observes state and why only one terminal outcome can take effect. A rollback removes the successful decision, so retry reevaluates time.
6. Walk through the persisted idempotency claim. Explain how a duplicate on another instance waits on a database unique key, how a new snapshot sees the completed response, and why a mismatched fingerprint is a conflict. Replay returns the original result without extending TTL. Explain why a different key still cannot bypass booking uniqueness.
7. Open the confirmation transaction and point to capacity transfer, hold consumption, booking fields, audit, outbox and completed response. Then demonstrate rollback before commit. Publication has not started inside that transaction.
8. Run the publisher crash test. The consumer commits; the publisher exits before marking; a new process reclaims the expired lease and sends the same MessageId. The inbox prevents another effective projection write. This is at-least-once delivery with a transactional idempotent effect, not end-to-end exactly-once delivery.
9. Explain stale lease tokens. A slow old publisher may finish after a new owner; its update cannot overwrite the new owner's outcome. Duplicate delivery remains safe. Explain classified failures, durable quarantine and audited re-drive, including why lifetime claims differ from the observed-failure budget. Discuss the remaining limits: no lease heartbeat or implemented payload-repair tool.
10. Run the expiry restart test. The original process is absent when the original stored deadline passes. A new process reads due work from PostgreSQL and releases capacity once. No process-local timer owns the work.
11. Defend RabbitMQ using the seven dimensions in ADR-002. Explain when retained replay or streaming would change the choice. Make the distinction between the executable local adapter and the proposed real broker adapter explicit.
12. Discuss hot voyages at 5,000 requests/second. More API instances do not remove serialization on one voyage row. Explain bounded database concurrency, short transactions, admission control, routing, retry amplification, connection pools and backlog metrics. Do not claim measured throughput that the repository has not demonstrated.
13. Describe the future payment process: no remote call while holding capacity locks; durable authorization coordination; idempotent local confirmation; void authorization if capacity consumption fails; reconcile unknown provider outcomes.
14. Explain the actual AI assistance and one correction from the AI note. Personally review every component and run the demonstrations before claiming ownership of its validation.

Prepare concise answers to these follow-ups: What if the response is lost after commit? What if the expiry worker is down? What if two different keys name the same booking? What if a consumer crashes after inserting its inbox row but before commit? What if a message is delivered after its publisher lease expires? What would break if booking and capacity moved to separate databases? Each answer should identify a concrete transaction, durable constraint, retry rule or documented limitation.

## Revision review and live ownership exercise

Start with the [assessment remediation map](assessment-remediation.md). The previous 88.5/100 score belongs to the assessed snapshot. The revised code requires fresh review, and the candidate's personal ownership remains unverified until demonstrated.

1. Trace background expiry, confirmation after the deadline and late cancellation into `HoldExpiryTransition.ApplyAsync` and `VoyageCapacity.ExpireHold`. Explain which code owns the rule and which code owns locks, persistence and commit.
2. Predict the fairness test before running it: more than one original batch of old holds belongs to a locked hot voyage, and a later cold voyage is due. Identify the retained cursor, fixed cutoff, bounded candidate budget and wrapping behavior. Show cold progress before releasing the hot lock and explain how skipped hot work is eventually revisited.
3. Explain an internal poll deadline: attempting a candidate is not resolving it. Demonstrate rollback and a later retry, then show why a zero-progress budget timeout must not refresh successful worker health. Contrast that with an empty successful scan and with bounded traversal past busy candidates.
4. Walk through Pending, Published and Quarantined state, lifetime attempts, cycle failures and state versions. Predict an old lease outcome arriving after a new owner quarantines and an operator re-drives. Show the exact guarded update and retained audit evidence.
5. Use the runbook to explain ActionId replay and expected-version conflicts. Describe why actor metadata is not authentication, why uncertain operator outcomes reuse the same action, and why re-drive cannot fix payloads or alter a previously consumed downstream result.
6. Explain why migration 001 must remain unchanged. Show the populated-upgrade test preserving old business data and publications, then explain checksum rejection and version-aware readiness without editing migration history.

For personal validation, the reviewer should choose an unprepared, bounded change in a sensitive path. Examples include a per-voyage share within the existing expiry budget or a new precisely classified delivery failure. The candidate must first state the intended behavior and failure cases, add or adapt a real PostgreSQL regression, implement the change and run the affected tests plus the required sensitive regressions. Preserve lock order, post-lock time, atomic persistence, duplicate protection and bounded resource use.

Record what the candidate actually explained, predicted, changed and executed, including mistakes and remaining uncertainty. A walkthrough document, an agent-written fix or memorized answers cannot establish personal ownership. The reviewer determines whether the live work demonstrates safe independent judgment; this document does not mark that stage passed.
